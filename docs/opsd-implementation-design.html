Implement OPSD in Miles, then prove parity

Full-vocabulary distillation on student trajectories · pinned reference code · direct edits to the vendored Miles tree

TL;DR: Implement the original OPSD distribution loss in Miles, beginning with the published frozen-base-teacher, LoRA recipe. First compare the loss and its gradients against the original function; then compare identical-token model forwards and optimizer steps. Only after those pass should independently generated trajectories be compared. This replaces the earlier sampled-token-loss proposal for the first implementation.

1. The first implementation is a reference port

Use the existing Miles Megatron actor and SGLang rollout, adding an explicit opsd_loss objective. The original repository is a validation oracle, not a second trainer copied into Miles. Preserve the existing Miles sampled-token OPD behavior. The two objectives must remain distinguishable in configuration and metrics.

Version 1: Qwen3 dense models; fixed base teacher; canonical LoRA student; full vocabulary; synchronous student rollouts; PP=1 and CP=1; TP=1 first, TP=2 after numerical validation. Generalized divergence math can cover the reference's β branches, but the initial recipe uses β=0. Do not mix PI/checkpoint ablations, EMA, MOPD, full-parameter training, long native-thinking runs, or a new PI generator into the reproduction milestone.

This is a design deliverable. No OPSD training implementation or GPU validation is claimed complete. The larger scientific study remains behind its existing experiment-review gate, and its previous compute projection must be revisited for full-vocabulary scoring.

3. Match the actual loss, including its quirks

p = softmax(student_logits / τ)
q = stop_gradient(softmax(teacher_logits / τ))
d[t,v] = q[t,v] · (log q[t,v] − log p[t,v])          # β = 0

L = Σ[t,v] mask[t] · min(d[t,v], c) / Σ[t] mask[t]  # clipping enabled
L = Σ[t,v] mask[t] · d[t,v] / Σ[t] mask[t]          # unclipped

The inspected loss function clips each vocabulary contribution before summing, has no extra τ² multiplier, and uses valid-token normalization for labeled “batchmean.” β=1 selects reverse KL; interior β uses its specified weighted mixture. Negative individual contributions remain negative, so the clipped sum need not be nonnegative. Do not silently replace this with clipping a summed token KL, PPO clipping, or response-mean reduction.

Distributed normalization needs a separate proof. With unequal valid-token counts, averaging independently normalized reference microbatches/ranks differs from a global valid-token mean. First match the original grouping, DP topology and accumulation schedule. Then test a global-token reducer against an independently aggregated oracle as a separate, explicitly named behavior. Do not let Miles' default sum-of-response-means or dynamic rebatching choose the objective implicitly.

For TP, normalize across the complete real vocabulary, excluding padded vocabulary entries before log-sum-exp. Keep student normalization differentiable, reduce teacher and student normalizers across TP, clip each local vocabulary element, then sum across TP exactly once. No full-vocabulary all-gather is required. Verify backward scaling as well as forward values; ordinary detached collectives are insufficient for student gradients.

The current native teacher path collects sampled log probabilities from the ordinary student sequence. A custom loss callback alone therefore cannot implement this port: it needs both privileged input tokens and vocabulary-level teacher targets. Keep those additions local; do not fork checkpointing, scheduling or the optimizer into another trainer.

Target contract: store detached teacher log-probabilities normalized over the real vocabulary at the declared loss temperature, with shape [response_positions, local_vocabulary]. Index each row by stable sample ID and response index, so independent teacher/student length sorting cannot pair the wrong targets. Record the teacher checkpoint/version, rollout version, vocabulary shard interval and true vocabulary size. Reject missing or stale keys and temperature mismatches; do not apply temperature twice. Keep input tokens flat with explicit sequence boundaries.

Bound memory honestly

Start with a correctness path that writes each teacher response block to a worker-local CPU target store immediately. Preserve FP32 target values for the FP32 parity contract, with sample ID, rollout/model version, temperature, vocabulary interval and response indices. Stage only the active student microbatch's targets on GPU, retaining them through its backward pass before release. Avoid caching the whole rollout batch on GPU or passing dense targets through the object store.

This limits target residency to a microbatch, but does not remove total target storage cost. At batch 32, vocabulary 151,936 and FP32, response targets alone occupy about 18.55 GiB at 1,024 tokens or 148.38 GiB at 8,192 tokens before TP/DP partitioning. Model logits, activations, copies and optimizer state are additional. Enforce CPU-cache and GPU-microbatch budgets and reject oversized configurations. An ordinary chunked loss forward can retain every target chunk for autograd, and does not prevent full prompt-logit materialization. Measure both peaks; true bounded chunked backward would be a later, independently gradient-validated optimization.

After parity, optimize scoring by bounded prepass groups or a separate frozen scorer if needed, with identical-target tests. Do not quietly introduce top-k truncation or reduced target precision as a memory fix. These change the validated numerical contract.

5. Alignment, frozen teacher and LoRA equivalence

  • Common response, separate offsets. Carry flat token arrays and sequence boundaries. A response token has one response index, but different student and teacher absolute offsets. Compare suffix token IDs exactly; select the preceding logits for next-token prediction. Never slice both views using one prompt length.
  • Prompt oracle. Compare rendered templates and tokenizer outputs with the original collator. Keep optional temporary padding inside the reference adapter; do not make padded tensors the Miles-wide representation.
  • Padding and EOS audit. The reference masks tokens by pad-token ID; if pad and EOS coincide, this affects EOS supervision. Its right-padded prompts and vLLM decode/re-tokenize step also need explicit unequal-length fixtures. First establish model-forward parity with one example per microbatch. For multi-example edge cases, export the original attention masks, positions and logit indices. Treat any mismatch as an unresolved compatibility result, not as an assumed reference bug.
  • Do not copy accidental batching behavior silently. If packed Miles and the literal reference differ on these fixtures, document a minimal reproducer. A corrected packed protocol needs a separately labeled comparison and review; it is not strict end-to-end equivalence to the unchanged reference.
  • Frozen base teacher. The author implementation disables student LoRA adapters for the teacher pass. A Miles snapshot is equivalent only if every adapter contribution is zero and the base weights match. Verify teacher logits against the unadapted HF base both before and after a student update. Merely loading base weights into a model with live adapters is insufficient.
  • Canonical adapters. Use Miles' existing canonical_lora mapping for independent Q/K/V and gate/up projections. A fused shared-rank adapter is not generally equivalent to the HF recipe. Import identical adapter tensors, validate projection permutations and alpha/r scaling, and compare effective weight updates after export—not unrelated raw tensor layouts.
  • No teacher autograd. Teacher targets and weights remain detached. Check that teacher parameters have no gradient and do not change after an optimizer step. Do not swap weights between a student forward and its backward.

CPU cases must cover β=0, β=1 and an interior β; clipped/unclipped loss; temperatures 1 and 1.1; noncontiguous logits; unequal lengths; padded vocabulary; negative contributions; empty masks; and teacher-gradient isolation. Use independent analytic gradient or finite-difference checks away from clipping boundaries, not just two copies of the same formula. An all-masked global batch should fail clearly; a rank with no valid tokens must participate safely when the global batch is nonempty. Record this intentional guard if the reference returns NaN.

For tiny-model FP32 comparisons, propose loss tolerance 1e-5 absolute + 1e-4 relative and mapped-gradient relative L2 error ≤1e-3. Near-zero tensors need absolute error checks. BF16 thresholds must first be calibrated from unchanged-model repeat runs and fixed before judging a port. Any relaxed threshold requires a documented numerical reason; do not calibrate it from a failed port until it passes.

A full reference-framework job uses an isolated original environment and the actual trainer. Extracting its loss function is only Level A. Two implementations sharing the newly written kernel are not independent validation. Public test fixtures use synthetic or explicitly public content; runtime traces stay local.

7. Two-worker execution and review gates

Use neutral labels worker-a and worker-b in every public artifact. Their real addresses, names, storage paths and reservations stay in ignored local configuration.

  1. Design review: agree on original-objective parity first, the fixed-teacher LoRA scope, compatibility boundaries and acceptance criteria. No algorithm patch or runtime test is claimed by this design commit.
  2. CPU implementation: write the loss oracle tests, new kernel, prompt/response contracts and launcher snapshots. These can be completed without GPU experiments.
  3. Bounded validation pilot after approval: worker-a runs the isolated original/HF checks; worker-b runs Miles. Share only immutable local fixtures and checkpoint artifacts. Repeat one fixture in both environments on both workers to expose host effects. Separate runtime environments; do not overwrite either dependency stack.
  4. Gate report: publish sanitized aggregate errors, pass/fail status, code/model/tokenizer pins, resource totals and unresolved mismatches. Missing or failed gates prevent a reproduction claim.
  5. Scientific experiments: only after parity and a reviewed resource estimate, revisit the PI/checkpoint matrix. Repeat later with matched thinking modes and an explicitly chosen loss/reduction. Approval of a correctness pilot does not authorize the full run.

The previously proposed 64 GPU-hour pilot ceiling remains a maximum proposed allocation, not approval or a completion estimate. Full-vocabulary target costs and the isolated reference environment may require a smaller pilot scope. The previous sampled-token full-study schedule is superseded as an executable proposal.

Initial pilot scope: tiny-model checks use fixed short synthetic sequences; the 4B bridge uses a fixed set of 32 eligible public math problems, an identical-token one-step check, then at most 10 replay updates and 10 fresh-rollout updates per framework. Begin at microbatch one and accumulate the same logical batch; record its difference from the published eight-rank, microbatch-four recipe. Use short synthetic cases for distribution/topology checks before the 4B bridge. Keep the reference 1,024-token response cap and impose a reviewed input-token cap that fits both runtimes. This is a correctness and cost pilot, not evidence of learning gains or a reproduction of the full training result. Stop when the scope or the resource ceiling is reached, whichever comes first.

After parity, the scientific follow-up can score the same response under current/frozen checkpoints and PI/no-PI contexts. That four-cell comparison separates context effects from checkpoint effects without changing the rollout trajectory. Its loss, thinking-mode controls and compute matrix need their own revision and review.

8. Planned explicit implementation commits

  1. Reference fixtures and loss kernel: source pins/checksums, independent oracle adapter, dense divergence and meaningful CPU tests.
  2. Paired prompt/response data: original-template checks, typed fields, response index alignment and edge-case fixtures.
  3. Megatron teacher targets and loss integration: frozen-base validation, bounded target store, dispatch, distributed scaling and startup checks.
  4. Canonical LoRA and replay validation: adapter mapping, identical-token forward/update harness, distributed regression tests.
  5. Public recipe and sanitized report: Python launcher, launch snapshots, local configuration example with placeholders, validation results and limitations.

Commit directly to main with one focused change per commit. Keep source import provenance intact. The loss and data interfaces should be usable by later PI/checkpoint work, but version 1 should not implement that entire research matrix.

9. Public-data boundary

Allow only public source/model references, neutral worker labels, relative example paths, synthetic/public fixtures and reviewed aggregate metrics into the repository. Exclude personal identity information, actual hardware codenames and hostnames, private endpoints, node/cluster/reservation IDs, private filesystem paths, credentials, raw logs and operational screenshots. Do not publish real identifiers inside a scanner denylist. Check author and committer metadata before each public push.

Required upstream copyright notices and public scholarly attribution remain intact. These precautions prevent new operational disclosures; they do not anonymize a named public repository or erase existing Git history.

10. Evidence and unresolved questions

  • Original compute_loss and data collator: authoritative reference behavior.
  • Current Miles OPD signal; forward-only and training execution; loss scaling.
  • Canonical adapter target mapping: useful existing support, still requiring numerical validation.

Open issues: literal reference behavior on unequal-length prompts; EOS/pad supervision; resolved optimizer/accumulation semantics; HF-to-Megatron canonical-adapter parity; precision-specific tolerances; teacher target-cache throughput. These are validation tasks with explicit failure outcomes, not assumptions that the port already works.

Completed for this design: source inspection and checksum verification, architecture review, memory arithmetic, privacy checks and document validation. No loss/gradient parity test, model forward, training step or GPU benchmark has run.
